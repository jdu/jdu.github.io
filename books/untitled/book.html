Bio

Jeff Uren is a software engineer, data architect and engineering leader with more than twenty years of experience building large-scale systems across healthcare, scientific research, finance, embedded software and distributed platforms.

His work has ranged from operating systems and embedded devices to cloud-native data platforms, federated analytics and semantic architectures. During the COVID-19 pandemic he contributed to the architecture and technical review of multiple clinical trial data-sharing platforms supporting international vaccine research, and has since led the design of semantic data platforms and organisational ontologies within the research sector.

Throughout his career Jeff has been less interested in individual technologies than in the organisations that build and depend upon them. His work increasingly focuses on the intersection of software architecture, enterprise architecture, systems thinking and knowledge representation, exploring how organisations can preserve shared meaning while continuing to evolve.

He is the creator of the Unified Domain Architecture (UDA), a practical approach to modelling organisational meaning independently of individual systems, and is an advocate for treating architecture as a discipline of stewardship rather than governance.

When he isn't designing systems, Jeff writes about architecture, organisations and technology, with a particular interest in the relationship between language, complexity and change. His writing draws inspiration from fields as varied as cybernetics, military sustainment, philosophy, ecology and literature, reflecting a belief that the hardest problems in architecture are rarely technical alone.

Indirection

Pointers, references, interfaces, proxies, lookup tables, DNS, dependency injection, handles, symbolic links, IDs.

Software engineering uses indirection constantly because it lets us change what something refers to without changing everything that refers to it.

But every additional level also makes the system harder to follow.

That's almost architecture in miniature.

Benath The Software

Not a computer-science survey. More like opening the bonnet and following the pipes.

28.1 The Machine Underneath

Start with:

application ↓ runtime / libraries ↓ system calls ↓ kernel ↓ CPU / memory / storage / devices

What a process really is. Virtual memory. Threads. File descriptors. Sockets. Filesystems. Scheduling.

Enough that things like “the database opened 500 connections” stop being abstract statements.

28.2 From Source Code to Running Program

Take several paths:

Rust/C/C++ → compiler → executable → loader → process

Java/C# → compiler → bytecode → runtime → process

Python → interpreter → modules → process

JavaScript → runtime/JIT → process/browser

What compilation, linking, loading, interpreters and runtimes actually mean.

This gives people a much better instinct for what frameworks are sitting on top of.

28
33
28.3 What Happens When You Click the Button?

This could be one of the signature chapters of the book.

Follow one request all the way through:

mouse ↓ OS ↓ browser ↓ JavaScript ↓ HTTP ↓ DNS ↓ TCP / QUIC ↓ TLS ↓ network ↓ load balancer ↓ server ↓ application ↓ database ↓ disk

Then come all the way back.

Do variants for a desktop application and mobile application.

That single chapter could teach more useful architecture intuition than fifty diagrams of microservices.

There are several other areas that I think represent experienced-engineer knowledge rather than conventional architecture curriculum.

28.4 Data Is Bytes Eventually

People should understand the descent:

Customer ↓ object ↓ record ↓ JSON / protobuf / Avro ↓ bytes ↓ packet / file / page

Encoding, serialization, schemas, endianness at least conceptually, compression, framing.

It explains an enormous number of engineering decisions.

28.5 Processes, Threads and Work

A lot of engineers can use async frameworks without having a solid model of what is happening.

Processes, threads, event loops, coroutines, parallelism, concurrency, blocking, scheduling, synchronization.

Not “here's how to write pthreads.”

Rather: these are the different ways computers can arrange work.

28.6 Networks Are Machines Too

Networks shouldn't just appear as arrows.

Packets, routing, DNS, ports, TCP, UDP, TLS, proxies, NAT, load balancers, connection pools.

And especially:

A network call is not a function call with a longer arrow.

That lesson alone prevents a lot of bad architecture.

28.7 The Problem of Time
34

I'd expand the earlier time chapter considerably.

Clocks, ordering, timeouts, retries, deadlines, leases, TTLs, eventual consistency.

Experienced distributed-systems engineers eventually discover that time is part of the data model.

28.8 Queues Mean Pressure

Queues, buffers and backpressure.

The important lesson isn't how Kafka works.

It is:

producer faster than consumer ↓ somewhere something accumulates

Every system answers the question “where does excess work go?”, whether intentionally or accidentally.

28.9 Caches Create Two Truths

A wonderfully practical chapter.

Caching isn't fundamentally a performance technique.

The moment you cache something, you have created another representation of state and therefore a synchronization problem.

That kind of framing is exactly what I think this book should teach.

I'd also add some less glamorous areas that experienced engineers eventually realise are architecture.

28.10 Configuration Is Software

Environment variables, configuration files, feature flags, secrets, runtime configuration.

Configuration often becomes an undocumented programming language.

You can design it badly.

28.11 Deployment Is Part of the Design

An application isn't merely its source tree.

source → build → artefact → package → deploy → configure → execute → observe → upgrade

If it can't be deployed, upgraded and rolled back sanely, that is an architectural property.

28.12 Versioning and Compatibility

This deserves much more emphasis than most software books give it.

35

Schemas evolve. APIs evolve. files survive old programs. Messages remain in queues. Mobile clients don't update immediately.

Teach people to ask:

What happens when two versions of this system exist at the same time?

Because eventually they will.

28.13 Errors Are Information

Not “exceptions versus result types.”

What failures mean.

When to propagate them, transform them, retry them, record them, hide them or stop.

There is a huge difference between:

couldn't connect

and:

we don't know whether the operation succeeded

Experienced engineers learn to notice that distinction.

28.14 Observability Is an Interface

Logs, metrics, traces, debugging interfaces, admin tools.

I would frame observability as:

The interface the running system provides to its maintainers.

Which fits sustainment beautifully.

28.15 Performance Is Shape

Avoid premature-optimization clichés.

Teach where performance actually comes from:

algorithms locality allocations serialization network round trips contention I/O batching caching parallelism

And especially how to find where the time actually went.

There are also a few more subtle chapters I'd want in a book like this.

28.16 Dependencies Are Decisions

Not “avoid dependencies.”

A dependency exchanges work today for obligations tomorrow.

Libraries, frameworks, SaaS products and platforms all belong on the same spectrum.

36
28.17 Every Abstraction Has a Floor

Eventually somebody has to understand the thing underneath.

ORM → SQL → database → filesystem → storage.

HTTP framework → HTTP → TCP → sockets.

Containers → processes → kernel.

This could become one of the recurring visual motifs of the book: keep lifting the floorboards.

28.18 Interfaces Outlive Implementations

One of those things you really learn after maintaining systems for twenty years.

The implementation everybody agonised over disappears.

The weird API decision survives for fifteen years.

28.19 Data Usually Lives Longer Than Code

Same idea.

You will rewrite the application before you rewrite twenty years of business records.

That should radically change how people think about schemas and migration.

28.20 Reversibility

Not everything needs to be extensible.

But decisions with enormous blast radii should ideally be reversible.

This gives people a much healthier design heuristic than “future proofing.”

And I think there is one major practical engineering part still missing from our outline:

28.21 Working the Problem

How experienced engineers actually attack something unfamiliar.

Chapters like:

Reproduce It — make the behaviour observable.

Reduce It — remove everything that isn't necessary.

Trace It — follow data and control flow.

Measure It — don't diagnose performance from intuition.

Change One Thing — preserve causality while investigating.

Read the Source — eventually the documentation runs out.

37

Cross the Abstraction Boundary — when something impossible happens, descend a layer.

Build a Toy Version — sometimes twenty lines teach you more than twenty pages of documentation.

Those are incredibly transferable engineering skills, from somebody tinkering with a Raspberry Pi through to somebody responsible for a distributed platform.

And that leads to what I think could be the real promise of the book:

It isn't trying to make someone a software architect.

It's trying to make them the kind of engineer who, when confronted with something unfamiliar, can take it apart mentally, understand the forces acting upon it, see the choices available, and work their way downward until nothing is magic anymore.

That feels very consistent with the workshop-manual/Jeep Doctor idea.

Make the Machine do the Repetition

You've taught people what code is made from; now you show them how engineers can manipulate those building blocks at a higher level.

Make the Machine Do the Repetition

The basic principle:

Humans should make decisions. Machines should repeat them.

Start with mundane duplication, then show the spectrum:

copy and paste

function ↓ generic function ↓ template / generic type ↓ macro ↓ code generation ↓ domain-specific language

Each step is essentially saying:

“I have recognised a repeated structure and want to encode the structure rather than its instances.”

That's a very architectural concept.

40.1 Functions Aren't the Only Abstraction

This is where macros become interesting.

Most introductory programming implicitly teaches:

If something repeats, make a function.

But sometimes what repeats isn't runtime behaviour. It's program structure.

40
53

Rust makes this particularly visible.

You might contrast:

functions — abstract runtime behaviour generics — abstract over types traits — abstract capabilities/relationships declarative macros — abstract repeated syntax/structure procedural macros — transform or generate program structure build-time generation — manufacture artefacts before compilation

That gives people a much richer picture of the available design space.

54

Macros

I'd definitely give these their own chapter.

Not a Rust tutorial, but use Rust heavily because it has unusually good examples.

Show why something like:

#[derive(Debug, Serialize, Deserialize)] struct Person { name: String, age: u32, }

is enormously powerful.

Those three attributes may generate hundreds of lines of mechanically predictable implementation.

The engineer specifies intent and structure, rather than manually reproducing machinery.

Then explain the different flavours:

Declarative macros — reusable syntactic structures.

Derive/procedural macros — inspect program structure and generate code around it.

Attribute macros — transform how something behaves or is interpreted.

And importantly, macros aren't merely about saving typing.

They can enforce uniformity.

Templates and Generation

Then broaden outward.

Templates can generate:

41
55

source code configuration SQL schemas deployment manifests documentation APIs clients serialization layers

This leads into an important principle:

Generate the boring parts from the authoritative parts.

If your schema already describes something, perhaps five other representations shouldn't be manually maintained.

That's a huge sustainment lesson.

56

Declarative Versus Imperative

This fits beautifully here too.

Instead of telling a machine how:

create this then create that then connect them then configure this

you sometimes describe what should exist:

these are the things these are their relationships

Then another system determines how to produce the result.

SQL, HTML, CSS, Terraform, build systems, parser grammars and Kubernetes manifests all demonstrate variations of this idea.

Not “declarative is better.”

Rather:

Moving the mechanism elsewhere can give you enormous leverage—but you've also surrendered some control and visibility.

That's exactly the kind of trade-off your book wants to teach.

42
57

Small Languages

This could be another wonderful chapter.

Engineers eventually discover that sometimes the best abstraction is not another class hierarchy.

It's a tiny language.

Regular expressions are one.

SQL is one.

Format strings are one.

Routing definitions can become one.

Configuration can accidentally become one.

And eventually:

rule when customer.age > 65 apply senior_discount

You have created a language whether you intended to or not.

Then teach people to recognise the threshold:

When configuration gains conditions, variables, references and composition, you are probably designing a programming language.

That's experienced-engineer knowledge.

43
58

Encode Decisions, Not Just Repetition

This is where I'd distinguish the whole section from productivity.

The best leverage often isn't:

“This saved us writing 300 lines.”

It's:

“Nobody has to remember to do this correctly anymore.”

Examples:

type system enforces an invariant macro generates consistent registration formatter eliminates stylistic decisions linter catches prohibited structures schema generates serialization build system calculates dependency order compiler checks exhaustiveness migration tool tracks database state

You're moving knowledge from people's heads into machinery.

That connects directly back to sustainment.

44
59

The Cost of Magic

And this needs to be the counterweight.

Macros, generators, frameworks and metaprogramming can make five lines represent five thousand.

That's wonderful until something breaks.

5 lines written ↓ 5,000 lines implied ↓ 20,000 behaviours possible

So teach people to ask:

Can I see what was generated? Can I debug through it? Can I understand when it runs? Can I escape it? Can I replace it? Does knowing the abstraction save more understanding than it costs?

That last question is probably the heart of it.

Compression has a decompression cost

I might actually use that phrase in the book.

Macros and abstractions compress knowledge.

#[derive(Serialize)]

contains a lot of implied behaviour.

For someone familiar with it, that's excellent compression.

For someone debugging an edge case without understanding the machinery, they now have to decompress the abstraction mentally.

That's not an argument against abstraction. It's a way of understanding its cost.
