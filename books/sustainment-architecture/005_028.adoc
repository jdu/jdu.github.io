= Give meaning a language

The previous chapter asked you to identify the handful of things that remain true regardless of how your organisation changes. Those invariants describe what the organisation is. They do not yet describe what the organisation knows about those things or how they relate to one another.

That is the purpose of this chapter.

Every organisation already has a language. People speak about applications, grants, projects, people and organisations every day. The problem is not that the language doesn't exist. The problem is that it usually exists only in conversation. It changes slightly from team to team, acquires different meanings in different systems and is rarely written down in a form that everyone can agree upon.

The goal is not to invent a new language.

It is to make the existing one explicit.

== Recognising the problem

A useful way to test whether your organisation has a shared language is to ask different teams to describe the same concept without referring to a system.

Ask what an Application is.

One team may describe a request for funding. Another may describe a software application. A third may begin explaining how Salesforce stores the record rather than what the concept actually represents.

None of these people are necessarily wrong.

They are simply describing different things using the same word.

These differences often remain invisible because each team spends most of its time talking to itself. The disagreement only becomes visible when systems need to exchange information or reports need to combine data from different parts of the organisation.

By then the language problem has become a technology problem.

== Describe the organisation, not the database

A common mistake when designing a data model is to begin with tables.

The database already contains columns, identifiers and foreign keys, so it feels natural to organise discussions around those structures. The result is usually a model that faithfully describes one particular implementation while saying very little about the organisation itself.

Reverse the process.

Describe the organisation first.

What are the important concepts?

What do we know about each one?

How are they related?

Only after those questions have been answered should you consider how a particular database, CRM or ERP might choose to represent them.

The distinction matters because systems are implementations.

They are not reality.

A CRM does not create a grant. An ERP does not define an employee. A database does not determine whether two organisations are related. These systems simply record observations about things that already exist.

The map is not the territory.

An ontology exists because the map changes far more often than the territory beneath it.

== Describe concepts

Begin with the invariants identified in the previous chapter.

Each invariant becomes a concept within your shared language.

Keep the description short and independent of any implementation.

For example:

Concept	Description
Grant	A commitment by the organisation to provide funding under agreed conditions.
Person	An individual who participates in the organisation's work in one or more roles.
Organisation	A legal or informal body that interacts with the organisation.

At this stage you are not designing databases.

You are creating a vocabulary that allows people to describe the organisation consistently.

== Describe attributes

Once the concepts are clear, identify the information that belongs to each one.

Attributes describe the concept.

They do not describe how a particular system happens to store it.

For a Grant this might include:

Attribute	Description
Identifier	A stable identifier for the grant.
Title	A human-readable description.
Awarded Amount	The agreed funding value.
Award Date	The date on which the commitment was made.

Notice that these descriptions avoid implementation details.

Whether one system stores a date as a timestamp and another as text is irrelevant.

Those are implementation choices.

The attribute itself belongs to the organisation, not the software.

== Describe relationships


Relationships are often the first thing lost when organisations rely entirely on databases to describe themselves.

A foreign key tells one system how two rows are connected.

It says very little about what that connection means.

Make the relationship explicit.

Instead of saying

grant.organisation_id

say

A Grant is awarded to one or more Organisations.

Instead of

application.person_id

say

An Application is submitted by one or more People.

Once relationships are described in the language of the organisation they become understandable to people as well as software.

They also become reusable across every system that represents the same concepts.

== Give values meaning

Many attributes can only take one value from a known set.

* Status
* Country
* Currency
* Funding Type

These should be treated as controlled vocabularies rather than free text.

The purpose is not consistency for its own sake.

It is preserving meaning.

If one system records Awarded, another records Approved and a third records Successful, somebody eventually has to decide whether those values represent the same thing.

Making that decision once, deliberately, is far cheaper than making it independently in every report, integration and migration.

== Organise the language

As the number of concepts grows, they naturally begin clustering around different areas of the organisation.

* People
* Funding
* Finance
* Research
* Governance
* Technology

These are domains.

Domains exist to make the language easier to navigate.

They should not become barriers.

A concept belongs to one domain because that is where it is primarily understood, not because other domains are forbidden from using it.

The organisation should still have one shared language.

Domains simply provide structure as that language grows.

== Avoid reflecting your systems

The strongest temptation during this work is to allow an existing system to define the model.

This usually happens without anyone intending it.

The first CRM becomes the definition of a customer.

The finance platform becomes the definition of money.

The HR system becomes the definition of a person.

Once that happens every future system is expected to match the implementation choices of the first.

The organisation gradually forgets that the concepts existed long before the software did.

Always model the organisation.

Never model the product.

== Deliverable

At the end of this exercise you should have a document that describes your organisation independently of its technology.

It should contain:

* The core concepts that describe the organisation.
* The attributes that belong to each concept.
* The relationships between those concepts.
* Controlled vocabularies for values with agreed meanings.
* A small number of domains that organise the model as it grows.

The entire document should be understandable by someone who has never seen your systems.

If it reads like a database schema, you are describing an implementation.

If it reads like a description of the organisation itself, you are describing meaning.

* Principle: describe the organisation as concepts, attributes, and relationships before you describe a single table; the concepts exist before whatever system stores them does. * Practice: for each invariant from chapter 27, list its attributes, name its relationships to the other invariants explicitly instead of leaving them to be inferred from a foreign key, and turn any field that should only hold a fixed set of values into a controlled vocabulary; group related concepts into a handful of named domains so the model has somewhere to grow
* Pitfall: modelling columns instead of concepts, and letting whichever system was built first quietly become the definition everyone else has to match
* Takeaway: a one-page glossary of concepts, attributes, and relationships is worth more than a data dictionary generated from a database; one version of this, run in production, calls a concept a DirectClass, but the name matters less than doing it
