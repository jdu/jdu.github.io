Operand-Primal vs Operation-Primal

The core design choice at the heart of the Martin–Muratori debate. Both approaches solve the same problem — which direction of future change you expect determines which one costs you less.

The Expression Problem

Every system with n types and m operations has to choose one axis to optimise. You can't make both extensions free at the same time in a conventional type system — this is Philip Wadler's Expression Problem (1998).

Operand-Primal  (Bob's default)

  • Each type owns its own operations as methods
  • Interface declares the operations; every subclass implements them
  • ✓ Adding a new type — one new class, nothing else changes
  • ✗ Adding a new operation — must open the interface and every existing class

Natural in OOP languages. Works best when the set of operations is stable and the set of types grows over time (e.g. plugin systems).

Operation-Primal  (Casey's default)

  • Types are plain data (enum tag + struct fields)
  • Operations are standalone functions that match on the tag
  • ✓ Adding a new operation — one new function, nothing else changes
  • ★ Adding a new type — only update operations that need type-specific logic; generic operations (structural recursion, default: fallback) already work automatically

Natural in functional languages and Rust. Casey argues this works well in both directions: generic operations degrade gracefully for new types (like IO drivers returning "unsupported" for unknown opcodes), so only operations with type-specific semantics need updating.

Extension cost at a glance
Change Operand-primal (OOP) Operation-primal (data + functions)
Add a new type One new class Update only operations with type-specific logic; generic operations (case _:, structural recursion) already work — like old IO drivers hitting default: return UNSUPPORTED
Add a new operation Add to the interface + implement in every class One new function
Compile-time exhaustiveness check Missing method = TypeError at construction Missing match branch = silent runtime gap
Data layout control Objects scattered across heap, vtable overhead Flat structs, cache-friendly, SIMD-amenable
Batch processing / serialisation Need Command Pattern or visitor to treat ops as data Operations are already data; trivially batchable

🦀  Rust uses operation-primal as its default idiom

Rust's enum with pattern matching is exactly Casey's design, and it is what the Rust ecosystem reaches for first. The compiler also gives you exhaustiveness checking for free — a match that misses a variant is a compile error, closing the main weakness of the operation-primal approach. 

// Rust — operation-primal expression tree
enum Expr {
    Num(f64),
    Var(String),
    Add(Box<Expr>, Box<Expr>),
    Mul(Box<Expr>, Box<Expr>),
    Neg(Box<Expr>),
}

fn evaluate(expr: &Expr, env: &HashMap<&str, f64>) -> f64 {
    match expr {
        Expr::Num(v)      => *v,
        Expr::Var(n)      => env[n.as_str()],
        Expr::Add(l, r)   => evaluate(l, env) + evaluate(r, env),
        Expr::Mul(l, r)   => evaluate(l, env) * evaluate(r, env),
        Expr::Neg(e)      => -evaluate(e, env),
        // miss a variant → compile error: "non-exhaustive patterns"
    }
}

// Adding depth() costs one new function — nothing above changes:
fn depth(expr: &Expr) -> usize {
    match expr {
        Expr::Num(_) | Expr::Var(_) => 0,
        Expr::Add(l, r) | Expr::Mul(l, r) => 1 + depth(l).max(depth(r)),
        Expr::Neg(e) => 1 + depth(e),
    }
}

Rust's trait system lets you opt in to operand-primal selectively — implement a trait on a type to add operations to it after the fact, even from external crates. This is the closest existing language gets to solving the Expression Problem fully.

Python implementations — same problem, both designs

Both files evaluate the same expression ((x * 2) + (-y)) and produce identical output. Read the extension-test sections (marked with ══ banners) to see the cost of each change.

Operand-Primal operand_primal.py 
"""
Operand-Primal Design
=====================
The TYPE is the primary unit of organisation.
Each type owns all the operations it will ever participate in.

  Adding a new TYPE      →  cheap: one new class, nothing else changes   ✓
  Adding a new OPERATION →  expensive: open every existing class          ✗

This is Bob Martin's preferred default.  In OOP languages it is also the
natural grain of the language (inheritance, virtual dispatch, polymorphism).

Domain: a simple expression tree.  The same problem is solved identically
in operation_primal.py — compare the two to see the tradeoff directly.
"""

from __future__ import annotations
from abc import ABC, abstractmethod
from dataclasses import dataclass


# ── The contract: every Expr supports these operations ───────────────────
#    Adding an operation here forces a change in EVERY concrete class below.

class Expr(ABC):
    @abstractmethod
    def evaluate(self, env: dict[str, float]) -> float: ...

    @abstractmethod
    def pretty(self) -> str: ...

    @abstractmethod
    def variables(self) -> set[str]: ...


# ── Concrete types ───────────────────────────────────────────────────────
#    Each type is self-contained: it owns its own behaviour.

@dataclass
class Num(Expr):
    value: float

    def evaluate(self, env): return self.value
    def pretty(self):        return str(int(self.value) if self.value == int(self.value) else self.value)
    def variables(self):     return set()


@dataclass
class Var(Expr):
    name: str

    def evaluate(self, env): return env[self.name]
    def pretty(self):        return self.name
    def variables(self):     return {self.name}


@dataclass
class Add(Expr):
    left:  Expr
    right: Expr

    def evaluate(self, env): return self.left.evaluate(env) + self.right.evaluate(env)
    def pretty(self):        return f"({self.left.pretty()} + {self.right.pretty()})"
    def variables(self):     return self.left.variables() | self.right.variables()


@dataclass
class Mul(Expr):
    left:  Expr
    right: Expr

    def evaluate(self, env): return self.left.evaluate(env) * self.right.evaluate(env)
    def pretty(self):        return f"({self.left.pretty()} * {self.right.pretty()})"
    def variables(self):     return self.left.variables() | self.right.variables()


@dataclass
class Neg(Expr):
    operand: Expr

    def evaluate(self, env): return -self.operand.evaluate(env)
    def pretty(self):        return f"(-{self.operand.pretty()})"
    def variables(self):     return self.operand.variables()


# ════════════════════════════════════════════════════════════════════════
#  ADDING A NEW TYPE — the operand-primal sweet spot
#
#  Drop in one new class below.  evaluate(), pretty(), variables() are all
#  implemented here.  The Expr base class and every other type are untouched.
# ════════════════════════════════════════════════════════════════════════

@dataclass
class Pow(Expr):
    base:     Expr
    exponent: Expr

    def evaluate(self, env): return self.base.evaluate(env) ** self.exponent.evaluate(env)
    def pretty(self):        return f"({self.base.pretty()} ^ {self.exponent.pretty()})"
    def variables(self):     return self.base.variables() | self.exponent.variables()


# ════════════════════════════════════════════════════════════════════════
#  ADDING A NEW OPERATION — the operand-primal pain point
#
#  Goal: add depth() — the maximum nesting level of an expression.
#
#  To do this cleanly you must:
#    1. Add `def depth(self) -> int: ...` to the Expr abstract base class
#    2. Implement it in Num, Var, Add, Mul, Neg, AND Pow
#
#  That is 7 files touched for one new operation (in a real codebase, many more).
#  Below we add it as a standalone function using isinstance matching as a
#  workaround — but this bypasses the type system and doesn't scale.
# ════════════════════════════════════════════════════════════════════════

def depth(expr: Expr) -> int:
    """Standalone workaround — avoids opening every class, but is not OOP."""
    match expr:
        case Num() | Var():                      return 0
        case Add(l, r) | Mul(l, r) | Pow(l, r): return 1 + max(depth(l), depth(r))
        case Neg(operand):                       return 1 + depth(operand)
        case _:                                  raise TypeError(f"Unknown expr: {type(expr)}")


# ── Demo ─────────────────────────────────────────────────────────────────

if __name__ == "__main__":
    # (x * 2 + (-y))  with x=3, y=1  →  5.0
    expr = Add(Mul(Var("x"), Num(2)), Neg(Var("y")))
    env  = {"x": 3.0, "y": 1.0}

    print("┌── Operand-Primal ─────────────────────────────┐")
    print(f"│  expr      = {expr.pretty():<32} │")
    print(f"│  variables = {str(expr.variables()):<32} │")
    print(f"│  evaluate  = {expr.evaluate(env):<32} │")
    print(f"│  depth     = {depth(expr):<32} │")
    print("└───────────────────────────────────────────────┘")

    # Extension: Pow was added for free — nothing else changed
    expr2 = Pow(Var("x"), Num(3))
    print(f"\n  New type Pow: {expr2.pretty()} = {expr2.evaluate(env)}")
Operation-Primal operation_primal.py 
"""
Operation-Primal Design
========================
The OPERATION is the primary unit of organisation.
Types are plain data (tagged structs); behaviour lives in standalone functions.

  Adding a new OPERATION →  cheap: one new function, nothing else changes  ✓
  Adding a new TYPE      →  only update functions that need specific logic  ★

Casey's key insight: operations divide into two kinds:

  GENERIC operations work on any type via structural recursion or a
  `case _:` fallback — adding a new type requires ZERO changes here.

  TYPE-SPECIFIC operations have distinct logic per type — adding a new
  type means one new branch in each of those functions, nothing else.

  IO-driver analogy: add opcode RIO_trim to an OS IO subsystem.
  Old drivers hit  default: return UNSUPPORTED  — zero recompilation.
  In the vtable design every one of 1000+ drivers needs recompiling.
"""

from dataclasses import dataclass, field
from enum import Enum, auto

class ExprKind(Enum):
    NUM = auto()
    VAR = auto()
    ADD = auto()
    MUL = auto()
    NEG = auto()
    POW = auto()   # ← added in extension section

@dataclass
class Expr:
    kind:     ExprKind
    value:    float      = 0.0
    name:     str        = ""
    children: list       = field(default_factory=list)

def num(v):          return Expr(ExprKind.NUM, value=v)
def var(n):          return Expr(ExprKind.VAR, name=n)
def add(l, r):       return Expr(ExprKind.ADD, children=[l, r])
def mul(l, r):       return Expr(ExprKind.MUL, children=[l, r])
def neg(e):          return Expr(ExprKind.NEG, children=[e])
def pow_expr(b, e):  return Expr(ExprKind.POW, children=[b, e])


# ── TYPE-SPECIFIC — one branch per type needed ───────────────────────────

def evaluate(expr, env):
    match expr.kind:
        case ExprKind.NUM: return expr.value
        case ExprKind.VAR: return env[expr.name]
        case ExprKind.ADD: return evaluate(expr.children[0], env) + evaluate(expr.children[1], env)
        case ExprKind.MUL: return evaluate(expr.children[0], env) * evaluate(expr.children[1], env)
        case ExprKind.NEG: return -evaluate(expr.children[0], env)
        case ExprKind.POW: return evaluate(expr.children[0], env) ** evaluate(expr.children[1], env)
        # future unknown type: case _: return float("nan")  ← graceful degradation

def pretty(expr):
    match expr.kind:
        case ExprKind.NUM:
            v = expr.value; return str(int(v) if v == int(v) else v)
        case ExprKind.VAR: return expr.name
        case ExprKind.ADD: return f"({pretty(expr.children[0])} + {pretty(expr.children[1])})"
        case ExprKind.MUL: return f"({pretty(expr.children[0])} * {pretty(expr.children[1])})"
        case ExprKind.NEG: return f"(-{pretty(expr.children[0])})"
        case ExprKind.POW: return f"({pretty(expr.children[0])} ^ {pretty(expr.children[1])})"
        case _:            return f"<{expr.kind.name}>"  # ← graceful degradation


# ── GENERIC — already work for ANY type, including POW ───────────────────

def variables(expr):
    # case _: recurse over children — handles any compound type automatically
    match expr.kind:
        case ExprKind.VAR: return {expr.name}
        case ExprKind.NUM: return set()
        case _:            return set().union(*(variables(c) for c in expr.children))


# ════════════════════════════════════════════════════════════════════════
#  ADDING A NEW OPERATION — the operation-primal sweet spot
#  depth(): write one function. Everything above is untouched.
# ════════════════════════════════════════════════════════════════════════

def depth(expr):
    # Structural recursion — works for any type, no cases needed.
    # Adding POW required ZERO changes here.
    if not expr.children: return 0
    return 1 + max(depth(c) for c in expr.children)


# ════════════════════════════════════════════════════════════════════════
#  ADDING A NEW TYPE (POW) — what actually changed:
#
#    ExprKind.POW = auto()        in the enum           ← 1 line
#    def pow_expr(b, e)           constructor            ← 1 line
#    case ExprKind.POW:           in evaluate()          ← 1 line
#    case ExprKind.POW:           in pretty()            ← 1 line
#    variables()                  already worked         ← 0 changes
#    depth()                      already worked         ← 0 changes
#
#  Compare operand-primal adding one OPERATION (e.g. depth()):
#    abstract base + every concrete class = N+1 implementations
# ════════════════════════════════════════════════════════════════════════


if __name__ == "__main__":
    expr = add(mul(var("x"), num(2)), neg(var("y")))
    env  = {"x": 3.0, "y": 1.0}

    print("┌── Operation-Primal ───────────────────────────┐")
    print(f"│  expr      = {pretty(expr):<32} │")
    print(f"│  variables = {str(variables(expr)):<32} │")
    print(f"│  evaluate  = {evaluate(expr, env):<32} │")
    print(f"│  depth     = {depth(expr):<32} │")
    print("└───────────────────────────────────────────────┘")

    print("\n  ── New OPERATION: depth() — added for free ──")
    deep = add(add(add(var("x"), num(1)), num(2)), num(3))
    print(f"  depth({pretty(deep)}) = {depth(deep)}")

    print("\n  ── New TYPE: POW — what already worked without changes ──")
    p = pow_expr(var("x"), num(3))
    print(f"  pow_expr: {pretty(p)} = {evaluate(p, env)}")
    print(f"  variables({pretty(p)}) = {variables(p)}  ← generic, zero changes")
    print(f"  depth({pretty(p)})     = {depth(p)}         ← generic, zero changes")

The debate in one sentence: Bob defaults to operand-primal because he expects types to proliferate; Casey defaults to operation-primal because operations are flat data — directly serialisable, batchable, and bufferable without any additional patterns.

Casey's nuance on the "adding types is hard" criticism: Only type-specific operations need a new branch. Generic operations that recurse over structure, or that return a safe default for unknown types (analogous to an IO driver's default: return UNSUPPORTED), require zero changes when a new type is added. The real asymmetry is in the vtable direction: adding a single new virtual method to an interface forces every existing class to be updated or recompiled — including a thousand device drivers that don't support the new operation at all.

Both agree the choice should be deliberate and context-dependent. The disagreement is about which one to reach for first — and about whether the traditional Expression Problem framing accurately captures the real-world costs.
